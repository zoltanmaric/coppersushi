COPPER SUSHI / PARKED DRAFT

Make the data understandable.

An idea board for a possible data catalog. Not an approved implementation spec.

Status: deferred. Keep this draft in the reorganization PR stack for discussion. Nothing here needs to be implemented, finalized or completed in that stack. It does not block the migration or reorganization.

← Copper Sushi architecture

The problem

S3 files are hard to discover and interpret. We want a clear view of what datasets exist, what they mean, which dates they cover, and how they were produced.

Possible home for internal explainers

The current idea is to host this at coppersushi.121gigawatts.org/admin/data-catalog, or a similar path. Future internal explainers could live alongside it under /admin/. This is a tentative direction, not a committed route or hosting decision.

Whether these pages need restricted access is still undecided; the /admin/ path alone does not make them private.

Ideas to explore

  • A read-only page in the Copper Sushi frontend, perhaps at /admin/data-catalog, with code under frontend/datasets/.
  • Browse datasets and dates; inspect purpose, units, fields, coverage and publication time.
  • Preview a few rows, download a publication, or open its map.
  • A generated JSON index links to schemas and complete publication manifests. Load previews only when requested.

These are options, not a committed feature list. The current reorganization should not create an empty datasets folder or a placeholder route for them.

Possible data design

An index could list dataset ID, title, description, update frequency, schema URL, available dates and manifest links. Each manifest would identify a complete generation and its files. Separate per-dataset indexes could prevent producers overwriting each other’s entries.

One starting option is to keep S3 and add this inventory without a new serving database. The existing grid preparation database serves a different purpose. Raw caches, private preparation inputs and deployment archives would stay outside a public catalog.

Questions before committing

  • Who needs this: maintainers, public users, or both?
  • Would documentation and a simple inventory be enough, or is a browsing page useful?
  • Which datasets and metadata should be public?
  • Do we need previews and downloads, or just descriptions and links?
  • Who owns index updates, validation and missing-date reporting?

Revisit separately. Map schemas, manifests and safe publication remain requirements of the main migration; a cross-dataset catalog does not.
