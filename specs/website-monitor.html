Know when a page stops working.

Every 30 minutes initially, one AWS Lambda concurrently opens the blog, Critical Elements ⚡️ and Power Flow 🍣 in headless Chromium. A concurrent uncached HTTP request checks Ghost behind the public cache. CloudWatch evaluates the results and sends outage and recovery emails through SNS.

Problem

A running server can still serve a broken website. Check what a visitor receives, including browser errors and data requests. Keep the checker outside the Hetzner server and independent of the application process.

What counts as loaded?

Load the public entry pages a visitor uses. Each gets a fresh browser context and a bounded wait for meaningful content; a successful HTTP response alone does not pass. Check all three even when one fails.

Production readiness contract

Both CopperSushi pages expose data-load-state on their application root: loading, ready or error. Derive it from real React data and rendering state, not a test-only flag or a one-time console message. The blog keeps its visible-content check.

ready means required data is available and the map has finished rendering the current selection. Reset readiness when the selection changes; ignore completion from an older render. Required data or rendering failures produce error. Optional background prefetches do not hold a usable current view in loading.

Build on the existing Plotly completion callback. During the first implementation check, verify whether it covers underlying asynchronous map loading and use the map’s completion signal if needed. Playwright waits for ready, checks map visibility and independently captures errors. This establishes lifecycle completion, not pixel-level visual correctness.

Check Ghost behind the cache

Main now includes automatic Ghost recovery after MySQL restarts and public HTML caching with a one-day stale-on-error window. These are repository changes, not proof of live deployment. See the hosting runbook and cache policy.

Keep the anonymous homepage browser check unchanged: it measures public readability. In the same invocation, make one bounded HTTP GET to https://121gigawatts.org/?uptime=1. The tracked Cloudflare and Nginx policies bypass HTML caching for query strings. Verify that policy is active, the query survives redirects, and this response is not served from cache before relying on it. Require a successful HTML response with site content; a reachable proxy alone does not pass.

Give this probe its own CloudWatch alarm with the same failure and recovery policy. Name the alarm “Ghost origin path unavailable” and explain in its description that cached public pages may still be readable. The separate homepage alarm reports public readability; no custom cross-alarm message assembly is needed. The probe still traverses Cloudflare, so it does not diagnose which component failed. Do not add a fourth browser journey, direct-IP access, login, or a new health endpoint.

What triggers an email?

Capture console errors, uncaught JavaScript errors, failed requests and HTTP error responses from navigation until readiness plus a short observation window. HTTP errors use Playwright’s built-in response event; transport failures use requestfailed.

  • Fail the page: navigation failure, unsuccessful final document response, readiness timeout, uncaught application exception, or a failed required script, stylesheet or initial data request.
  • Keep as diagnostics: other console errors and optional-resource failures. A favicon or analytics failure alone does not declare an outage.
  • Keep exceptions narrow: add them only after observing a harmless failure. An expected unpublished-data response is not automatically an outage, but it does not prove the map loaded. Settle that default-page case before activation.

With regular metric delivery, two failed periods trigger an alarm. At the initial 30-minute cadence, detection takes roughly 30–60 minutes, plus evaluation and email delivery delay. Missing runs are handled by a separate checker alarm.

Cost and initial settings

Target less than $5/month. Start with one 2 GB Lambda every 30 minutes; parallel checks are the chosen starting design, with no comparative benchmarking phase. Make the interval configurable from 5 to 60 minutes, and derive both check-alarm and heartbeat periods from it.

Planning estimate: about $3.90/month at 30 seconds billed per run, or $5.40 at 60 seconds. This assumes a 30-day month, x86 compute at $0.0000166667 per GB-second and roughly $2.50 for metrics, alarms, image storage and modest logs/email. It does not rely on available Lambda free tier. These are assumptions, not measured performance; region, tax and extra website/map-provider usage can change the total. Sources: Lambda, CloudWatch and ECR pricing.

After deployment, report observed billed duration, memory use and projected monthly cost from normal runs. Keep running and adjust cadence or memory later if needed; a runtime comparison or tuning exercise is not an activation prerequisite. The $5 target is not a hard spending cap. Keep image and log retention bounded.

Runner and managed alert contracts
  • Start with 2 GB memory and a 30-minute schedule. Launch one headless Chromium process and run all three page checks concurrently in isolated contexts, alongside the Ghost HTTP probe. Collect each result independently; a rejected check must not cancel the others. Proposed limits: 45 seconds per page, a 3-second post-readiness observation window, a 10-second Ghost HTTP deadline, and a 240-second invocation timeout. Bound every wait, close the browser and prevent overlapping runs.
  • Before navigation, suppress Cloudflare Web Analytics in each monitor browser context using narrowly matched Playwright request routing. The production loader currently loads https://static.cloudflareinsights.com/beacon.min.js; verify the blog’s injected beacon too. Prevent analytics collection without adding production opt-out flags or blocking application, map or data resources. Mark deliberately blocked analytics requests as monitor exclusions, not failures.
  • Publish Failed as 0 (pass) or 1 (fail) for each of the four fixed check IDs. Use the scheduled slot’s timestamp, not retry time, so duplicate invocations cannot create a second failed period. Use the Maximum statistic: conflicting duplicate results conservatively fail that slot. Bound retry age and reject stale scheduled work rather than reporting old results as current health.
  • Each check has a standard CloudWatch alarm: period matching the configured schedule (initially 1,800 seconds), Maximum ≥ 1, two evaluation periods and two datapoints to alarm. Publish both successes and failures. Set missing-data handling to ignore; absence is not evidence of recovery. CloudWatch’s native evaluation/lookback rules apply rather than a custom exact incident counter.
  • Send ALARM and OK transitions to one SNS email topic. Stable ALARM periods do not deliberately repeat messages. Accept native delivery semantics, possible duplicates and an initial OK notification; do not build a notification state machine to suppress them. Confirm the private recipient’s SNS subscription before activation.
  • Use clear alarm names and descriptions containing the monitored URL and a logs-console link. Emails are the standard AWS alarm format; detailed browser errors and run timestamps stay in CloudWatch Logs. Do not promise a custom diagnosis or calculated outage duration in the email. Set explicit log retention; no screenshots.
  • Publish a completed-run heartbeat only after all four results have been published. A separate CloudWatch alarm treats absent heartbeats as breaching, targeting two missed scheduled periods. Verify actual missing-data evaluation delay during acceptance. A page failure is still a completed run; a crash, missed schedule or failed metric publication must not look healthy.
  • AWS hosting is independent of Hetzner but shares a provider with CopperSushi. Prefer a different AWS region where practical; a provider-wide outage remains a known blind spot.
Verified baseline and design choices

Frontend tests use Vitest; the React view tests use jsdom, mocked requests and a substituted map renderer. They cannot verify deployed browser rendering. Keep them unchanged. The browser monitor may later run in CI, but CI integration is not required here.

The deployment runbook owns current hosting, routes, data publication and private deployment-state discovery. Follow it before deployment. Do not create replacement state or copy credentials into this spec.

Choose Playwright for its browser and error-capture APIs. Selenium adds no required capability here. A managed uptime service remains a fallback if the browser packaging becomes disproportionate.
