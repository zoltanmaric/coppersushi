# Agent harness engineering

An agent harness gives the model tools, context, a working environment and feedback. Design it around the result the user needs and the evidence that lets the agent report completion. An evaluation harness runs that setup on controlled tasks and grades the results. Copper Sushi's spec and review practices have their own [workflow design](agent-workflow-design.md).

## Principles

| Design principle | What it changes |
|---|---|
| **Make the next useful action easy to find.** | Link from the point of work to the owning instructions, runbook or test. Give tools focused results that show what changed and how to recover from a failure. Keep detailed traces available for diagnosis. [OpenAI harness engineering](literature/openai-harness-engineering.md) · [SWE-agent interface](literature/swe-agent.md#interface) |
| **Put each check where it can catch the failure.** | Validate objective invariants at the boundary that can reject a bad action or result. Use instructions for choices that require judgment or user intent. Give failures enough detail for the agent to act. A successful tool call can still produce a result the user did not ask for. [SWE-agent ablations](literature/swe-agent.md#evidence) · [OpenAI harness engineering](literature/openai-harness-engineering.md) · [τ-bench](literature/tau-bench.md) |
| **Leave work a fresh session can verify.** | For work spanning sessions, use the task spec for the next decision, unfinished work and verification evidence. Let Git and the worktree show the changes. On resumption, check the actual state and run a core workflow before relying on an earlier completion claim. [Long-running agents](literature/effective-harnesses-for-long-running-agents.md) · [Copper Sushi workflow design](agent-workflow-design.md) |
| **Grade the outcome and any step that matters in its own right.** | Check the state the user will encounter. Use the trace for required approvals, the evidence behind completion claims and diagnosis of failures. Accept any route that meets those conditions. Test that the grader accepts a known good run and detects the failure it is meant to catch. [τ-bench](literature/tau-bench.md) · [Anthropic's evaluation guide](literature/demystifying-evals-for-ai-agents.md) |
| **Measure the change before keeping it.** | Replay an observed failure and a case where the intervention should stay idle. For a rule or tool comparison, hold the model, starting state, task, budget and grader fixed. Run fresh trials and compare how often all repeats succeed, time to completion and human intervention. A case can enter a replay after one failure. Persistent instructions follow Copper Sushi's [ablation rule](../AGENTS.md) and its [evidence record](rule-provenance.md). [SWE-agent ablations](literature/swe-agent.md#evidence) · [Repeated-trial reliability](literature/tau-bench.md#pass-k) · [Anthropic's evaluation guide](literature/demystifying-evals-for-ai-agents.md) |

SWE-agent isolates some tool-interface effects on coding issues. τ-bench measures outcome reliability in simulated service tasks, where a final-state match can miss a skipped approval. OpenAI's repository case and Anthropic's long-running demo show ways to expose runtime evidence and resume work. Their case reports leave the size of each intervention's effect open. The evaluation guide supplies methods for measuring those effects locally. [SWE-agent](literature/swe-agent.md) · [τ-bench](literature/tau-bench.md) · [OpenAI case report](literature/openai-harness-engineering.md) · [Anthropic demo](literature/effective-harnesses-for-long-running-agents.md) · [Anthropic's evaluation guide](literature/demystifying-evals-for-ai-agents.md)

## Worked example — hypothetical browser-verification replay

Copper Sushi once reported a preview ready when its shell returned HTTP 200 and showed a loading screen. The constraint layer then failed because the compiled catalog was missing. The existing rule requires evidence from the rendered page after relevant loads settle. [Observed failure](rule-provenance.md) · [Browser verification rule](../AGENTS.md)

1. Reset the same Critical Elements ⚡️ preview and ask the agent to verify that a known mapped constraint can be selected. Serve a fixed day with known constraint data. In one case, delay its required metadata until after the shell loads. In another, fail that request to reproduce the load failure at the browser boundary. [Map readiness contract](../coppersushi/frontend/README.md) · [Constraint selection](copper-sushi-app.md)
2. In the complete case, require the map to reach `data-load-state="ready"` and show the expected contribution after selection. In the broken case, require the agent to identify the failed metadata request and report the feature as blocked. Check the rendered outcome and use the trace to catch premature claims or missed inspection. If browser evidence is unavailable, record the limit. [Map readiness contract](../coppersushi/frontend/README.md) · [Outcome and transcript grading](literature/demystifying-evals-for-ai-agents.md)
3. Compare the existing instructions with one change, such as making the existing readiness signal easier to find. Reset the preview before each trial. Count correct verifications and false ready claims across repeats. Use a documentation-only task to check that the change does not trigger irrelevant browser work. The replay is an example design with no measured result. [SWE-agent ablations](literature/swe-agent.md#evidence) · [Repeated-trial reliability](literature/tau-bench.md#pass-k)
