# Agent-driven design of forecasting systems

## Principles

Start the design by naming the consumer, the action they can still take, and the last useful issue time. These are design recommendations derived from the linked cases. Apply them to one forecast edition before choosing infrastructure.

| Design principle | What it changes |
|---|---|
| **1. Benchmark at the decision deadline.** | Replay the latest edition actually available when the consumer acted. A noon forecast cannot establish 11:00 skill, even on identical delivery quarters. [Energy-Arena paired example](price-forecasting/energy-arena-benchmarks.md#paired-week) |
| **2. Measure the service the customer received.** | Count every expected issue, including late, fallback and missing editions. Keep model-only scores alongside delivered-service scores and delivery coverage. [Participant fallback case](price-forecasting/operational-forecasting.md#service-performance) |
| **3. Control what changes when attributing a gain.** | Compare complete services to measure what changed for the consumer. To isolate a model change, give both models the same input editions, issue dates and truth. To isolate input freshness, hold the model and issue time fixed. [ECMWF release scorecards](price-forecasting/operational-forecasting.md#release-comparisons) · [Published intraday study and proposed feed test](price-forecasting/operational-forecasting.md#intraday-study) |
| **4. Carry uncertainty to the quantity the consumer uses.** | For a fleet or a multi-hour position, aggregate within each scenario before taking quantiles. Check interval width and misses on both sides by horizon and operating condition. [GenCast aggregation](price-forecasting/operational-forecasting.md#ensemble-aggregation) · [Aurora calibration](price-forecasting/operational-forecasting.md#calibration) |
| **5. Budget the whole path to delivery.** | Measure upstream waiting, computation and publication separately. Use the time left to decide whether a fresh run, partial output or fallback can still help. [MetDesk deployment](price-forecasting/operational-forecasting.md#delivery-latency) |
| **6. Define exactly what settles the forecast.** | Specify the product, interval, unit and truth version. A revised day-ahead forecast, an intraday auction forecast and a live trade index answer different questions. [Kpler product definitions](price-forecasting/operational-forecasting.md#price-editions) |
| **7. Preserve editions across the chain.** | Record which upstream editions produced each published forecast. An as-of query must still recover what the consumer could retrieve after a later revision arrives. [Kpler vintage queries](price-forecasting/operational-forecasting.md#price-editions) |
| **8. Use the same feature rules in training and serving.** | Build a historical example from the inputs eligible at that issue time using the live transforms. Test units, interval alignment and missing inputs at the boundary. [Google Cloud pipeline automation](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) |
| **9. Give training, release and issuing separate triggers.** | Fresh labels can trigger a fit. A validated candidate can replace the approved model. Fresh market or weather data can trigger another edition with the same model. Record which event happened. [Derivation from Google Cloud and Kpler](price-forecasting/operational-forecasting.md#pipeline-triggers) |
| **10. Define release and recovery evidence before automating.** | Decide which data, quality and serving checks block promotion. Retain the compatible model, features and code needed to restore service. Add automation when release frequency or a delivery obligation justifies it. [Google Cloud maturity levels](https://docs.cloud.google.com/architecture/mlops-continuous-delivery-and-automation-pipelines-in-machine-learning) · [Project deployment stages](price-forecasting/forecast-infrastructure.md) |

## Define the forecast contract

Write one sentence: “At **[decision time]**, **[consumer]** needs **[quantity and units]** for **[entity, place and future interval]**, expressed as **[point, quantiles or scenarios]**, to **[take an action]**.” Then name the source of the eventual observation, when it becomes available, and how revisions are handled. Ask the owner about choices that change the decision. Record assumptions the team can test.

The rows below illustrate choices an agent needs to resolve for each application.

| Forecast | A design choice that changes the system |
|---|---|
| Day-ahead power price | Identify the bidding zone, auction, local decision deadline and delivery quarters. A scheduled run can publish tomorrow’s curve once, with earlier editions retrievable. [DE–LU contract](price-forecasting/germany-luxembourg.md#contract) · [Published editions](price-forecasting/operational-forecasting.md#price-editions) |
| Intraday power price | Choose the auction clearing price or a precisely defined continuous-market quantity. For a volume-weighted price, specify the contract, trade window and outcome when no trades occur. Work backwards from the trader’s reaction time to choose periodic or event-triggered updates. [Kpler intraday products](price-forecasting/operational-forecasting.md#price-editions) |
| Wind, solar or load | Identify the site or fleet and whether the target is potential output, metered generation or demand. Record units, capacity changes and meter revisions. For fleet risk, combine sites within each weather scenario before taking quantiles. [GenCast aggregation](price-forecasting/operational-forecasting.md#ensemble-aggregation) |
| Weather | Choose the field, location, height, units and valid interval. An hourly mean irradiance and an accumulated radiation field need an explicit conversion. Score against a named observation or analysis version. [Weather input contract](price-forecasting/data-sources.md#weather) |
| Gas or oil price | Specify the hub or benchmark, currency, unit, delivery month and target price, such as a settlement or a window of trades. For a series spanning expiring contracts, define the roll rule. A contract switch can otherwise look like a forecast error. [ICE Dutch TTF contract specification](https://www.ice.com/products/82843860/ICE-Futures-Europe-Dutch-TTF-Natural-Gas-Futures) |

A fundamental can itself be a forecast product. If predicted wind generation feeds a price model, the generation service scores its edition against metered output. The price service records exactly which generation edition it consumed and scores its own output against the auction. Replay this chain using the upstream prediction available at the price deadline. Substituting realized generation tests a different system. [GenCast aggregation](price-forecasting/operational-forecasting.md#ensemble-aggregation) · [Kpler price editions](price-forecasting/operational-forecasting.md#price-editions)

## Design one edition end to end

1. **Draw the two clocks.** Mark source issue, actual receipt, decision deadline and customer-visible publication on one line. Mark the intervals being forecast on the other. Define the eligible revision at each join, including geography, units and interval boundaries. Record historical availability as witnessed, documented, assumed or unknown. Before a full replay, pass one real timestamped update through the normal feature path. Delay its receipt across the cutoff and verify that only subsequent editions can use it. [Point-in-time contract](price-forecasting/data-sources.md#point-in-time)
2. **Draw training and issuing separately.** State what triggers a fit, what authorizes its release, and what triggers a new prediction with the approved model. Show how training reconstructs the same features available when issuing. Fit transforms and calibration using only eligible training observations. Give each edition enough provenance to reconstruct its inputs, fitted model, code and settings. [Forecast storage and execution](price-forecasting/forecast-infrastructure.md)
3. **Specify the deadline behavior.** Budget time for upstream arrival, computation and delivery. Decide what the consumer gets if a feed is late, only part of a curve arrives, or the full ensemble misses the deadline. Define acceptable fallback age and how the consumer sees its status. Give a retry the same edition identity and a deliberate revision a new one. Test a lost publication acknowledgement by reading through the normal consumer interface. [Participant fallbacks](price-forecasting/operational-forecasting.md#service-performance) · [Publication retries](price-forecasting/operational-forecasting.md#publication-retries)
4. **Design evaluation before choosing a winner.** Select a simple reference available by the same cutoff. Replay historical issue times in order, align targets and truth versions, and compare on identical periods. Estimate the difference that decides the investment. For example, subtract weather-only loss from weather-plus-demand loss on each common issue and resample contiguous blocks of days together. Separate intervals against a common reference cannot answer this question. Separately score the editions actually delivered, record fallback use, and count missing or late forecasts over all expected issues. For uncertainty, pair a proper score with band widths, misses on each side, and counts by horizon and decision-relevant conditions. Use joint scenarios when the action depends on a path or fleet total. [Original DE–LU baseline controls](https://github.com/zoltanmaric/coppersushi/blob/3b834499fec2d855c0fa98c3aa9eac3574836802/wiki/price-forecasting/evaluation.md#controls) · [Strict full-input experiment policy](https://github.com/zoltanmaric/coppersushi/blob/e0e69142bf5bff05630852a4cd98081b6a927a16/wiki/price-forecasting/evaluation.md#defaults) · [Paired uncertainty and limitations](price-forecasting/evaluation.md#limitations)
5. **Choose the smallest architecture that meets the contract.** For research, a reproducible batch replay and frozen inputs can suffice. For a prospective trial, withhold the future observation. Start at the normal data collector and record when the consumer can first retrieve the edition. Compare that time with the deadline, then attach the observation and score the same edition. For a live service, name who responds, monitor delivery before truth arrives, and exercise rollback of the compatible model and features. Add streaming, a feature store or distributed inference when a stated requirement or measured bottleneck justifies it. Say what the consumer would notice if the simpler design were kept. [Storage selection principle](price-forecasting/forecast-infrastructure.md#selection-principle) · [Release comparisons](price-forecasting/operational-forecasting.md#release-comparisons)

## Work the design on a real decision

In the [DE–LU example](price-forecasting/energy-arena-benchmarks.md#paired-week), the same participant scored 11.44 €/MWh at 11:00 and 7.16 at noon across the same 672 quarters. The later edition could incorporate an intervening auction. For an 11:00 customer, this determines the serving interface: retrieve the last edition published by 11:00, retain its inputs, and score that edition after clearing. Weekly 50% interval coverage also hid one day with only 15 of 96 prices inside the band. That determines a monitoring view: show misses by delivery day alongside the aggregate score.

Finish with the contract, one traced edition, the baseline and release criteria, and the result that would change the design. If the claim concerns a consumer action, freeze its decision rule and evaluate its outcome on untouched dates alongside forecast accuracy. A second agent can review that design by replaying the example, delaying one input and reversing one release. Record which behaviors were demonstrated and which still need evidence.
